# 面试专题：MQ 可靠性与顺序性（RabbitMQ 与 Kafka）

## 一、概念说明

MQ 面试的核心是三件事：消息不能丢、不能重复消费、顺序要可控。RabbitMQ 与 Kafka 给出的答案机制不同，但思路一致。

### Q1：项目中哪里用到了 MQ？为什么选 RabbitMQ？

典型场景：发布内容的异步审核、验证码的异步发送、用户行为数据的异步采集入库、搜索历史记录的异步保存、用户信息修改后的跨服务同步（同步修改其他服务中冗余/缓存的数据）、静态化页面生成、MySQL 与 Redis/ES 之间的数据同步。

选型理由：异步解耦（服务间不再强依赖）、削峰填谷（突发流量先入队再匀速消费）、提高系统吞吐量。

### Q2：RabbitMQ 如何保证消息不丢失？

消息从发送到消费会经历多个环节，每一步都可能丢，RabbitMQ 分段给出方案：

| 环节 | 机制 |
| --- | --- |
| 消息发送到交换机丢失 | 发布者确认机制 publisher-confirm：发送失败向生产者返回 ACK，生产者通过回调接收结果，失败则重发或记录日志人工介入 |
| 交换机路由到队列丢失 | 发布者回执机制 publisher-return：路由失败返回失败原因，生产者回调处理 |
| 消息在队列中丢失 | MQ 持久化：交换机持久化、队列持久化、消息持久化 |
| 消费者消费消息丢失 | 消费者确认机制 + 消费者失败重试机制 |

极端情况（回调丢失、系统宕机、磁盘损坏）概率很小，要进一步提高成功率可以程序自控：**消息状态表**——表字段含消息 id、消息内容、交换机、路由 key、发送时间、签收状态。发送方业务执行完毕后先存一条"未签收"记录再发消息；消费方消费完毕后回一条签收消息；发送方收到后把状态改为已签收；定时任务扫描未签收消息重新发送，已完成的定时清理。

### Q3：消息的重复消费如何解决？

成因：发送失败或消费失败后的自动重试，都可能造成重复投递。解决方案分两层：

1. 每条消息设置唯一标识 id；
2. 幂等方案：token + Redis、分布式锁、数据库锁（悲观锁、乐观锁）。

### Q4：100 万消息堆积在 MQ 怎么办？

三种思路：

- **提高消费者的消费能力**：使用多线程消费；
- **增加更多消费者**：用工作队列模式，设置多个消费者消费同一个队列中的消息，提高消费速度；
- **扩大队列容积**：使用 RabbitMQ 惰性队列——接收到消息后直接存入磁盘而非内存，消费者要消费时才从磁盘读取加载，支持数百万条消息存储。

### Q5：RabbitMQ 如何保证消费的顺序性？

一个队列只设置一个消费者消费即可。多个消费者之间无法保证消息消费的顺序性。

### Q6：RabbitMQ 的延迟队列？

两种实现：

1. 消息过期 TTL + 死信交换机：消息在队列里过期后进入死信交换机，再路由到真实消费队列；
2. 延迟交换机插件。

设置消息过期也有两种粒度：为队列设置统一的过期时间；为消息单独设置过期时间。两者同时存在时以时间短的为准。注意：RabbitMQ 队列判断过期是看**队头元素**，如果队头消息过期时间很长，后面短过期时间的消息也要排队等它。

### Q7：什么是死信？死信交换机？

消息在以下情况会成为死信：被消费者拒绝且不重回队列、消息过期、队列达到最大长度。为队列绑定死信交换机（DLX）后，死信会被路由到 DLX 再进入死信队列，可以集中处理（记录、补偿、告警）。

### Q8：Kafka 如何保证消息不丢失？

同样分三段：

- **生产者 → Broker**：同步发送用 `get()` 等结果（阻塞、效率低），异步发送用回调（非阻塞、效率高，但可能回调丢失）；设置很大的重试次数；acks 三档——`acks=0` 不等任何响应（最快但可能丢）、`acks=1`（默认）首领节点收到即响应、`acks=all` 所有参与复制的节点都收到才响应；
- **Broker 存储**：分区多副本机制，副本分布在不同 Broker；主分区数据同步到副本之前宕机仍可能丢，配合 acks 解决；
- **消费者**：消费者靠 offset 定位消费位置，故障重平衡时若默认每 5 秒自动提交偏移量——提交偏移量小于实际处理位置会重复消费，大于则会丢失。解决：消费完毕手动提交（同步提交会阻塞但重试、异步提交不阻塞不重试、或两者结合）。

### Q9：Kafka 如何保证顺序性？

topic 分区内的消息只被消费者组中唯一一个消费者处理，所以**分区内有序，跨分区无序**。要全局顺序就只开一个分区；要业务级有序，发送时指定相同的消息 key——分区按 key 做 hash，相同 key 必然落在同一分区。

### Q10：Kafka 的高可用与高性能？

高可用：集群保证 Broker 高可用；分区多副本保证数据高可用；重平衡保证消费者高可用。

高性能来自：顺序读写、消息分区并行、页缓存（把磁盘访问变成内存访问）、零拷贝。写入链路：生产者 → Kafka → 操作系统页缓存 → 由系统决定何时刷盘。

### Q11：Kafka 的数据清理？

数据以索引（xxxx.index）和日志（xxxx.log）分段存储在磁盘。两种清理策略，任意一个满足即触发：`log.retention.hours=168`（默认保留 7 天）、`log.retention.bytes=1073741824`（默认 1G，超出删除最久数据），后台线程定期检查。

### Q12：Kafka 的点对点与发布订阅？

靠消费者组实现：多个消费者在**同一个组**，同一分区只被组内一个消费者消费——点对点；多个消费者在**不同组**，不同组的消费者都能收到同一分区的数据——发布订阅。

## 二、技术点之间的联系

- "不丢、不重、有序"是一个三角：可靠性拉满往往带来重复（重试、确认重发），顺序性拉满往往牺牲吞吐（单队列/单分区单消费者）——所以最终都要幂等兜底，按业务取舍。
- RabbitMQ 的 TTL + 死信既是延迟队列的实现，也是"坏消息"的收集通道，一个机制两用。
- Kafka 的重平衡同时是可靠性话题（offset 提交偏差）和顺序性话题（分区换主）的触发点，理解重平衡就理解了 Kafka 消费端一半的问题。
- RabbitMQ 惰性队列与 Kafka 的顺序写/页缓存，都是"用磁盘换内存"的思路——MQ 的容量和吞吐之争本质是内存与磁盘的取舍。

## 三、方法与实现要点

- 答可靠性时按"生产端 → Broker → 消费端"三段式组织，RabbitMQ 和 Kafka 通用；
- 答重复消费时先说成因（重试/自动提交 offset），再说缓解（手动提交），最后落到业务幂等（唯一 id + Redis/分布式锁/数据库锁）；
- 答顺序性时先界定范围（RabbitMQ 队列内、Kafka 分区内），再说突破手段（key 路由）；
- 答堆积时按"消费快一点（多线程）、消费者多一点（工作队列）、队列大一点（惰性队列）"三步回答。

## 四、重点与难点分析

- **重点 1**：RabbitMQ 的四段防丢机制（confirm/return/持久化/消费确认）与 Kafka 的三段（acks/副本/手动提交）要能对照着讲。
- **重点 2**：offset 提交偏差的两个方向——提交偏小重复、提交偏大丢失。
- **难点 1**：RabbitMQ 过期判断看队头——设置消息级 TTL 时，长 TTL 消息堵在队头会让短 TTL 消息"延迟过期"。
- **难点 2**：消息状态表方案的本质是"用数据库做可靠性的最后一公里"，属于本地消息表思想，与 MQ 自身机制是互补而非替代。
- **易错点**：认为 Kafka 全局有序（只有分区内有序）；认为惰性队列消费更快（它是拿速度换容量）。

## 五、示例

### 示例 1：RabbitMQ 四段防丢的配置清单

```text
生产端：publisher-confirm（到交换机）+ publisher-return（路由失败回执）
Broker： 交换机 durable=true、队列 durable=true、消息 deliveryMode=2（持久化）
消费端：手动 ack + 失败重试（或拒绝后进入死信队列）
兜底：  消息状态表 + 定时任务扫描未签收消息重发
```

### 示例 2：Kafka 手动提交 offset

```java
// enable.auto.commit=false
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
    for (ConsumerRecord<String, String> record : records) {
        handle(record);   // 先完成业务处理（含幂等校验）
    }
    consumer.commitSync();   // 消费完毕后手动提交
}
```

### 示例 3：按订单号保证局部有序

```java
// 同一订单的所有消息用 orderId 做 key，必然进入同一分区、被同一消费者顺序处理
ProducerRecord<String, String> record =
        new ProducerRecord<>("order-topic", orderId, orderJson);
producer.send(record);
```

### 示例 4：RabbitMQ 延迟队列的两种实现对比

```text
方案一：队列 x-message-ttl=30000 + x-dead-letter-exchange=dlx
       消息 30 秒过期 → 进入死信交换机 → 路由到真实队列被消费
方案二：延迟交换机插件，发送时指定 delay，到点自动投递
注意：队列级 TTL 与消息级 TTL 同时存在时以较短的为准；过期判断看队头
```
