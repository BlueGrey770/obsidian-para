# 面试专题：JVM 进阶

## 一、概念说明

JVM 面试的主线是四个问题：内存怎么分、类怎么加载、垃圾怎么收、回收器怎么选。

### Q1：JVM 运行时数据区有哪些？

组成：堆、方法区、虚拟机栈、本地方法栈、程序计数器。

1. **堆**：解决对象实例存储的问题，是垃圾回收器管理的主要区域。线程共享，保存对象实例和数组；堆中没有内存可分配且无法再扩展时抛 `OutOfMemoryError`。
2. **方法区**：可以认为是堆的一部分（逻辑上），存储已被虚拟机加载的类信息、常量、静态变量、即时编译器编译后的代码。
3. **虚拟机栈**：描述方法执行时的内存模型，线程私有，生命周期与线程相同。每个方法执行时创建栈帧，栈帧保存局部变量表、操作数栈、动态链接、方法返回地址。方法开始执行进栈、执行完出栈（相当于清空数据），所以这块区域**不需要 GC**。
4. **本地方法栈**：与虚拟机栈功能相同，区别是它服务于本地（非 Java）方法。
5. **程序计数器**：线程私有，保存当前线程所执行字节码的行号/地址。JVM 通过线程轮流切换分配执行时间，任何时间点一个处理器只执行一个线程；线程被挂起后再恢复时，靠程序计数器得知上次执行到哪里。它是 JVM 规范中**唯一没有规定 OOM 的区域**，也不会 GC。

### Q2：Java 堆的内部结构？

JDK7 中堆内分为年轻代、老年代和方法区（永久代）：

- Young 区划分为 Eden 区和两个大小严格相同的 Survivor 区。某一时刻只有一个 Survivor 被使用，另一个留作垃圾收集时复制对象用。Eden 区变满时 GC 把存活对象移到空闲的 Survivor 区；经过几次垃圾收集后仍存活的对象被移动到老年代（Tenured）。
- Tenured 区保存生命周期长的对象。
- 永久代保存类信息、静态变量、常量、编译后的代码。**永久代有大小限制**，大量动态生成类时很容易 OOM。

### Q3：JDK8 为什么用元空间替代永久代？

1. PermGen 内存经常溢出引发 OutOfMemoryError，JVM 希望这块内存被更灵活地管理，不再频繁 OOM；
2. 移除 PermGen 可促进 HotSpot 与 JRockit 的融合（JRockit 没有永久代）。

准确说：Java 7 之后永久代中的字符串常量池先被移到堆内存；Java 8 时 PermGen 被元空间（Metaspace）代替，类元信息、字段、静态属性、方法、常量等都移到元空间。元空间与永久代最大的区别是**元空间不在虚拟机中，而是使用本地内存**，默认情况下其大小仅受本地内存限制。

### Q4：什么是直接内存？

直接内存不受 JVM 内存回收管理，是虚拟机的系统内存，常见于 NIO 操作用作数据缓冲区。分配回收成本较高，但读写性能高。传统 IO 需要在堆中开辟空间做数据拷贝；NIO 使用直接内存，JVM 可以直接操作直接内存，数据读写传输更快（实测拷贝 100M+ 文件，NIO 比传统 IO 快数倍）。

### Q5：堆和栈的区别？

1. 栈内存存储局部变量和方法调用，堆内存存储 Java 对象和数组；堆会被 GC，栈不会；
2. 栈是线程私有的，堆是线程共享的；
3. 两者不足时都会抛异常，但类型不同：栈不足抛 `StackOverflowError`，堆不足抛 `OutOfMemoryError`。

### Q6：类加载器有哪些？类装载的执行过程？

类加载器用于装载字节码文件（.class）。常见四类：启动类加载器（Bootstrap，加载 JDK 核心类库）、扩展/平台类加载器、应用类加载器（加载 classpath 下的类）、自定义类加载器。

类装载的执行过程：加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载。

- 加载：通过类的全限定名获取字节码文件，转换为方法区内的运行时数据结构；
- 验证：校验字节码，确保符合虚拟机规范；
- 准备：为类的静态变量分配内存并设置默认初始值；
- 解析：将符号引用转换为直接引用；
- 初始化：执行类的初始化代码，包括静态变量赋值和静态代码块。

### Q7：什么是双亲委派模型？为什么采用？

类加载时，类加载器先把加载请求委派给父类加载器尝试加载，父类加载不了才自己加载。作用：保证类加载的**安全**（核心类库不会被自定义同名类篡改）、**防止重复加载**（同一类只会被加载一次）。

### Q8：对象什么时候可以被回收？

没有任何引用指向的对象就是垃圾。判定方式有两种：

- **引用计数法**：对象被引用一次计数加一，为 0 则可回收。优点是实时性高、回收时应用无需挂起；缺点是每次引用都要更新计数器、浪费 CPU，且**无法解决循环引用**（a、b 互相引用、外部都置 null 后仍不会回收，造成内存泄漏）。
- **可达性分析**（现在的虚拟机都采用）：从 GC Roots（局部变量、静态变量、常量、类信息等肯定不能回收的对象）出发向下遍历，与根对象没有直接或间接引用链的对象可回收。被标记为可回收的对象不会马上回收——如果还没执行过 finalize 方法，会先执行一次，执行中若重新与 GC Roots 建立关联可以"复活"（机会只有一次）。

### Q9：垃圾回收算法有哪些？

| 算法 | 过程 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 标记-清除 | 标记出可回收对象，再清除 | 解决了引用计数的循环引用问题 | 标记和清除都要遍历所有对象、GC 时要停应用；**内存碎片化严重** |
| 复制 | 内存一分为二，每次用一块；GC 时把存活对象复制到另一块，再整体清空 | 垃圾对象多时效率高；无碎片 | 同一时刻只能用一半内存，利用率低 |
| 标记-整理 | 在标记-清除基础上，把存活对象向一端移动后再清理边界外内存 | 无碎片 | 移动对象有额外成本 |
| 分代收集 | 堆分新生代和老年代：新生代用复制算法，老年代用标记-清除或标记-整理 | 按对象生命周期选算法 | — |

HotSpot 默认使用分代收集：新生代（Eden + 两个 Survivor）用复制算法并配对象晋升机制，老年代用标记-清除或标记-整理。

### Q10：四种引用类型的区别？

- **强引用**：最普通的引用，有强引用的对象 GC 不回收，内存不足宁可 OOM；
- **软引用**：内存足够不回收，内存不足时在 OOM 之前回收（适合做缓存）；
- **弱引用**：GC 扫描到只具有弱引用的对象，不管内存是否足够都会回收——ThreadLocal 的 key 就是弱引用，value 是强引用，key 被回收后 value 失去访问入口却占着内存，这就是 ThreadLocal 内存泄漏的根因，用完要调用清理方法；
- **虚引用**：必须配合引用队列使用，对象被回收时虚引用入队，用于感知回收并处理关联资源（如堆外内存）。

### Q11：常见的垃圾回收器？

| 回收器 | 区域 | 算法 | 特点 |
| --- | --- | --- | --- |
| Serial | 新生代 | 复制 | 单线程，回收时 STW |
| ParallelNew | 新生代 | 复制 | 多线程，JDK8 默认，STW 更短 |
| Parallel Scavenge | 新生代 | 复制 | 追求可控吞吐量，适合后台计算型任务 |
| Serial Old | 老年代 | 标记-整理 | 单线程，Client 模式用 |
| Parallel Old | 老年代 | 标记-整理 | 吞吐量优先，常与 Parallel Scavenge 搭配 |
| CMS | 老年代 | 标记-清除 | 并发回收，停顿最短，但有内存碎片 |
| G1 | 整堆 | 标记-整理 + 复制 | Region 化、可设最大停顿目标，JDK9 默认 |

CMS 四阶段：初始标记（STW，只标记 GC Roots 直接关联对象，快）→ 并发标记（与用户线程并发）→ 重新标记（STW，修正并发期间的变动）→ 并发清除。G1 取消年轻代/老年代的物理划分，把堆分成若干 Region，优先回收垃圾比例高的 Region；Mixed GC 只回收部分老年代，阈值默认堆占用 45%；超大对象进 Humongous 区。

## 二、技术点之间的联系

- 内存区域决定"谁会被 GC、谁来 GC"：堆是 GC 主战场，栈帧随方法结束自动销毁，程序计数器既不 OOM 也不 GC——三个区域的生命周期差异是理解 GC 范围的前提。
- 类加载把字节码放进方法区，执行引擎从方法区取指令、在栈中创建栈帧、在堆中创建对象——"加载→内存→执行"是一条完整链路。
- 可达性分析是判定，回收算法是动作，回收器是产品化组合：CMS = 标记-清除 + 并发，G1 = Region + 标记-整理/复制 + 可预期停顿。
- 四种引用强度给 GC 提供了回收优先级，软/弱/虚引用是"缓存、ThreadLocal、堆外内存回收通知"三个实战场景的答案。

## 三、方法与实现要点

- 答内存区域按"线程共享（堆、方法区）/ 线程私有（栈、本地方法栈、程序计数器）"二分组织，再逐一说存什么、会不会 OOM/GC。
- 答垃圾回收按"判定 → 算法 → 回收器"三层递进，别只背回收器名字。
- 答调优参数时至少能说出：`-Xms/-Xmx`（堆初始/最大）、`-Xmn`（年轻代大小）、`-XX:SurvivorRatio`（survivor:eden 比例）、`-Xss`（线程栈大小）。当 Survivor 区不够大或占用达到 50%，对象会提前进入老年代，合理设置 Eden/Survivor 可把年轻对象留在年轻代，避免 Full GC。
- 监控工具：jmap 生成堆转存快照、jstat 显示 GC 与类加载统计（关注 S0/S1/E/O/M 各区使用比例、YGC/YGCT、FGC/FGCT）。

## 四、重点与难点分析

- **重点 1**：程序计数器是唯一不 OOM 的区域——线程私有、只存行号，这句话能答出来说明理解了线程切换机制。
- **重点 2**：元空间用本地内存、不再受 `-XX:MaxPermSize` 限制，是"为什么 JDK8 干掉永久代"的核心答案。
- **难点 1**：finalize 的"复活"只有一次机会，且强烈不推荐依赖它做资源释放。
- **难点 2**：CMS 停顿短但留碎片，G1 用 Region 复制顺带压缩解决碎片——这是"G1 为什么取代 CMS"的关键论述。
- **易错点**：把"方法区"说成堆的物理部分（逻辑上属于堆，HotSpot 曾用永久代实现）；认为复制算法无代价（浪费一半内存）。

## 五、示例

### 示例 1：直接内存的性能对比（NIO）

```java
private static void directBuffer() {
    long start = System.nanoTime();
    try (FileChannel from = new FileInputStream(FROM).getChannel();
         FileChannel to = new FileOutputStream(TO).getChannel()) {
        ByteBuffer bb = ByteBuffer.allocateDirect(_1Mb);   // 直接内存缓冲区
        while (true) {
            int len = from.read(bb);
            if (len == -1) break;
            bb.flip();
            to.write(bb);
            bb.clear();
        }
    } catch (IOException e) {
        e.printStackTrace();
    }
    long end = System.nanoTime();
    System.out.println("directBuffer 用时：" + (end - start) / 1000_000.0);
}
```

同样拷贝大文件，传统 IO 用时约 1500ms+，直接内存 NIO 约 500ms 左右。

### 示例 2：可达性分析中的 GC Roots

```java
public class Demo {
    public static Demo a;   // 静态变量是 GC Root

    public static void main(String[] args) {
        Demo b = new Demo();
        b.a = new Demo();   // 该对象被静态变量 a 引用
        b = null;           // b 原指向的对象与 GC Root 断开，会被回收
                            // 而 a 指向的对象依然存活
    }
}
```
