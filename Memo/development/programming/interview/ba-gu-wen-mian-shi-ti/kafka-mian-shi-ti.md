# Kafka 面试题（可靠性、顺序性与高性能设计）

## 一、概念说明

Kafka 作为吞吐量优先的消息中间件，面试考察点集中在四条主线：消息不丢失、不重复消费、顺序性、高可用与高性能。库内八股文只有 RabbitMQ 体系，本篇补齐 Kafka 视角。

### 1. 消息不丢失的三段链路

消息从生产者到 Broker 再到消费者，每一段都可能丢：

- **生产者 → Broker 丢失**：设置同步发送或异步发送。同步发送通过 `get()` 获取发送结果，阻塞、效率低；异步发送通过回调获取发送结果，非阻塞、效率高，但可能出现回调丢失。此外设置消息发送失败的重试次数（设一个很大的值，失败不断重试）。
- **Broker 存储丢失**：Kafka 提供分区备份机制，为每个分区设置多个副本，主分区服务器宕机后副本分区仍有完整数据。但主分区数据同步到副本分区之前主分区宕机，仍可能丢消息，解决方案是设置消息确认的 ACKS。
- **消费者接收丢失**：消费者通过 offset 定位消费数据。消费者故障后触发重平衡，重新分配消费分区；重平衡过程中 Kafka 默认每 5 秒自动提交偏移量，会出现消息丢失或重复消费。

ACKS 确认机制：

| 取值 | 含义 |
| --- | --- |
| acks=0 | 生产者成功写入前不等待任何服务器响应，有丢失风险，但速度最快 |
| acks=1（默认） | 只要集群首领节点收到消息，生产者就收到成功响应 |
| acks=all | 所有参与复制的节点全部收到消息，生产者才收到成功响应 |

偏移量提交的两个方向：提交偏移量**小于**客户端处理的最后一条消息的偏移量，两条偏移量之间的消息会被重复处理；提交偏移量**大于**，两条之间的消息将会丢失。

### 2. 重复消费的成因与解决

成因同上一节的重平衡 + 自动提交偏移量。缓解方案：把自动提交周期调小（周期越小出问题概率越小，但对消费者性能和服务器压力影响越大，只能缓解，不能根治）。根治方向是消费完毕**手动提交偏移量**：

- 同步提交：会阻塞、效率低，但会重试直到成功；
- 异步提交：不阻塞、效率高，但不重试，可能提交失败；
- 同步异步结合。

即便这样，网络原因、服务器原因导致偏移量提交失败时仍可能重复消费，业务侧还要做幂等。

### 3. 顺序性

topic 分区中的消息只能由消费者组中的唯一一个消费者处理，所以单个分区内消息必然按先后顺序处理；但**不能保证跨分区的顺序**。因此要顺序处理 topic 的所有消息，就只提供一个分区。控制分区归属的两种方式：

1. 发送消息时直接指定分区；
2. 发送消息时指定消息 key，同一业务使用相同 key——分区是按 key 做 hash 计算得到的，相同 key 必然落在同一分区。

### 4. 高可用机制

- **集群**：通过集群模式保证 Broker 的高可用；
- **分区备份**：为每个分区设置副本（可手动指定副本数量），副本分布在不同 Broker 上，保证数据高可用；
- **重平衡**：消费者组新增消费者或消费者宕机时，为组内消费者重新分配消费分区，实现消费者的高可用。

### 5. 高性能设计

多方面的协同结果：宏观架构、分布式存储、ISR 数据同步、对磁盘与操作系统特性的高效利用。要点：

- **顺序读写**：磁盘顺序写的性能远高于随机写；
- **消息分区**：分区并行，提升吞吐；
- **页缓存（Page Cache）**：把磁盘数据缓存到内存，把对磁盘的访问变为对内存的访问；
- **零拷贝**：数据从内核缓冲区直接发送到网卡，避免在内核态与用户态之间反复拷贝。

写入与读取链路：生产者发消息给 Kafka → Kafka 把消息交给操作系统的页缓存 → 由系统决定何时把消息同步到磁盘（通常页缓存中数据较多时同步）。消费者监听 Kafka → Kafka 从页缓存读数据 → 页缓存没有则从磁盘读取到页缓存 → 拷贝给消费者。

### 6. 数据清理机制

Kafka 数据以索引文件（xxxx.index）和日志文件（xxxx.log）形式存于磁盘；日志分段存储，既减小单文件体积，也方便清理。两种清理策略（任意一个达到即删除）：

1. 按保留时间：`log.retention.hours=168`（默认 7 天），超过时间触发清理；
2. 按数据大小：`log.retention.bytes=1073741824`（默认 1G），topic 日志文件超过阈值时删除最久的消息。

Kafka 启动后台线程定期检查是否有可删除的消息。

### 7. 点对点与发布订阅

Kafka 的两种消息模式都靠**消费者组**实现：消费者组由一个或多个消费者实例组成，具备可扩展性和容错性。

- 点对点：多个消费者放在同一个组，同一分区数据只能被组内一个消费者消费；
- 发布-订阅：多个消费者处于不同组，不同组中的消费者都能消费同一分区的数据。

## 二、技术点之间的联系

- 可靠性三链路（生产端 acks + Broker 副本 + 消费端 offset 提交）与"重复消费"是同一套机制的两面：提高可靠性往往带来重复，压低重复又可能丢消息——最终都要靠**业务幂等**兜底。
- 顺序性与吞吐量互为代价：单分区保证顺序但牺牲并行度；按业务 key 分区是在"局部顺序 + 整体并行"之间的折中。
- 高性能设计里的页缓存与零拷贝，解释了"Kafka 为什么快"：顺序写规避磁盘寻道，页缓存把磁盘访问变成内存访问，零拷贝减少数据搬运次数。
- 消费者组既是负载均衡单元（点对点），又是广播单元（发布订阅），重平衡则是组成员变化时的重新分配动作——它同时是可靠性话题和顺序性话题的触发点。

## 三、方法与实现要点

### 1. 消息不丢失的标准答法

按链路分段回答：生产端（同步/异步发送 + 重试 + acks=all）→ Broker 端（多副本 + 副本同步确认）→ 消费端（关闭自动提交，消费完成后手动提交 offset）。最后补一句"极端情况（回调丢失、系统宕机、磁盘损坏）概率很小，还可以设计消息状态表 + 定时任务补偿"。

消息状态表方案：表字段含消息 id、消息内容、交换机、路由 key、发送时间、签收状态。发送方业务执行完毕后保存记录（状态未签收）再发消息；消费方消费完毕后回一条签收消息；发送方收到后把状态改为已签收；定时任务扫描未签收消息重新发送，已完成消费的定时清理。

### 2. 重复消费的标准答法

先讲成因（重平衡 + 自动提交 offset），再讲缓解（缩短提交周期），再讲根治（手动提交，同步/异步择一或结合），最后落到业务幂等：每条消息设置唯一标识 id、幂等方案、token + Redis、分布式锁、数据库锁（悲观锁/乐观锁）。

### 3. 顺序性的标准答法

"分区内有序、跨分区无序"→ 要全局有序就单分区 → 要业务有序就用相同 key 路由到同一分区 → 消费端单线程消费该分区。

### 4. 与其他 MQ 的选型对比

RabbitMQ 延迟低、路由灵活，适合业务解耦与延迟任务；Kafka 吞吐高、可回溯（按 offset 重放），适合日志采集、行为数据、流式处理。回答"为什么选 X 不选 Y"时，从吞吐、延迟、消息模型、运维成本四个维度讲，并落到业务量级。

## 四、重点与难点分析

- **重点 1**：acks 三档语义（0 / 1 / all）与"可靠性—吞吐"的取舍关系，必须能对应到具体场景。
- **重点 2**：偏移量提交的两种偏差方向——提交偏小导致重复、提交偏大导致丢失，这是判断候选人是否真理解 offset 的分水岭。
- **难点 1**：重平衡为什么既影响可靠性又影响顺序性。答案：重平衡期间分区归属变化，未提交的 offset 造成重复或丢失；分区换主后同一 key 的消费线程可能变化，若消费端多线程处理会打乱顺序。
- **难点 2**：零拷贝的原理表述。要点是减少内核态与用户态之间的数据拷贝次数，避免数据在应用层中转。
- **易错点**：认为"设置 acks=all 就一定不丢"——还要配合 `min.insync.replicas` 等副本侧配置；认为"Kafka 保证全局顺序"——它只保证单分区顺序。

## 五、示例

### 示例 1：手动提交偏移量的消费循环（伪代码）

```java
// 关闭自动提交：enable.auto.commit=false
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
    for (ConsumerRecord<String, String> record : records) {
        // 业务处理：先落库/幂等校验，再提交
        handle(record);
    }
    // 消费完毕后手动提交偏移量
    consumer.commitSync();   // 同步提交：阻塞但会重试；commitAsync 异步不重试
}
```

### 示例 2：按业务 key 保证局部顺序

```java
// 相同订单号作为 key，必然被 hash 到同一分区 → 同一消费者顺序处理
ProducerRecord<String, String> record =
        new ProducerRecord<>("order-topic", orderId, orderJson);
producer.send(record, (metadata, exception) -> {
    if (exception != null) {
        // 异步发送失败，记录日志并按重试策略重发
    }
});
```

### 示例 3：清理策略配置

```properties
# 按时间清理：保留 7 天
log.retention.hours=168
# 按大小清理：单个日志段上限 1G，超出后删除最久数据
log.retention.bytes=1073741824
# 两个条件任意一个满足即触发删除
```

### 示例 4：消费者组两种模式

```text
点对点：  order-service-group = [consumer1, consumer2]
          同一分区的消息只会被组内一个消费者处理（负载均衡）

发布订阅： group-A = [consumer1]   group-B = [consumer2]
          两个组都能收到同一分区的全量消息（广播）
```
