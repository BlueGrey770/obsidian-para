## 5）八股文（扩展到 12 题，全部给到“可背答案 + 深挖追问”）

### 1）OpenFeign 工作原理（怎么从接口调用变成 HTTP）

**Q：Feign 是怎么工作的？**  
**A（可背版）**：  
 OpenFeign 是声明式 HTTP 客户端。启动时扫描 `@FeignClient` 接口，为每个接口生成**动态代理**。当我调用接口方法时，Feign 会把方法上的注解（URL、HTTP 方法、参数、Header）解析成 `RequestTemplate`，再通过 `Encoder` 把入参序列化成请求体/Query；接着结合服务发现拿到目标服务实例列表，用负载均衡选一个实例发起 HTTP 请求；响应回来后用 `Decoder` 反序列化成 Java 对象。工程里通常会配置**超时、重试、日志**，并结合 Sentinel 做**熔断降级**走 fallback。

**追问 1：Feign 超时怎么配？为什么重要？**

- 超时一般分连接超时/读超时；不配或过大，会导致线程长时间阻塞，引发线程池耗尽，进而雪崩。  
**追问 2：Feign 能不能开重试？**
- 只建议对**幂等接口**开重试；像创建订单/派单这类非幂等操作，重试会造成重复写入。  
**追问 3：如何统一透传 tenantId/traceId？**
- 用 `RequestInterceptor` 给所有 Feign 请求统一加 Header（tenantId、traceId、auth token）。

### 2）Sentinel 熔断降级（3 状态 + 怎么落地）

**Q：Sentinel 熔断降级怎么做？**  
**A（可背版）**：  
 Sentinel 用于服务保护，核心是**限流、熔断降级、系统自适应保护**。熔断器通常是 **Closed/Open/Half-Open**：Closed 正常放行并统计慢调用/异常；超过阈值进入 Open，直接拒绝并走降级；过了窗口期进入 Half-Open，放少量探测请求，成功则恢复到 Closed，失败回 Open。项目里常把 Feign 或关键接口接入 Sentinel，配置慢调用比例/异常比例阈值，配合 fallback 返回兜底结果，避免依赖抖动拖垮主链路。

**追问 1：fallback 和 blockHandler 区别？**

- `blockHandler`：被 Sentinel 规则拦截（限流/熔断）时走；
- `fallback`：业务执行异常时走。  
**追问 2：阈值怎么定？**
- 先看历史 RT、P95、错误率；先保守，再灰度调参；核心接口更偏稳，非核心更激进。  
**追问 3：熔断后怎么恢复？**
- Half-Open 探测；恢复过程一定要限制探测流量，避免一恢复就被打爆。

### 3）RabbitMQ 可靠性（不丢、不重、可恢复）

**Q：RabbitMQ 怎么保证可靠投递？**  
**A（可背版）**：  
 RabbitMQ 默认语义是“**至少一次**”，所以可靠性要分三端：  
 1）**生产端**：开启 Confirm/Return；Confirm 确保消息到达 Broker，Return 确保路由到队列；发送失败记录失败表或本地消息表，定时补偿重发。  
 2）**Broker**：Exchange/Queue durable，消息 persistent 才能落盘；必要时用死信/延迟队列做重试。  
 3）**消费端**：手动 ACK；处理成功才 ACK，失败走重试；多次失败进入死信队列或失败表，后续人工/补偿任务处理。

**追问 1：怎么解决“业务落库成功但消息没发出去/发出去了但业务回滚”？**

- 最稳是 **Outbox（本地消息表）**：同一个本地事务写业务表+消息表；异步把消息投递 MQ，成功后更新消息状态；失败可重投。  
**追问 2：重复消费怎么办？**
- 幂等：每条消息带 `messageId/orderId/taskId`，消费前查“是否处理过”（Redis set/DB 唯一约束/幂等表），处理过直接 ACK 跳过。  
**追问 3：积压怎么办？**
- 提升消费者并发/水平扩容、拆分队列、优化慢消费（外部接口/DB慢）、必要时对生产端限流。

### 4）MQ 顺序性（怎么回答“消息顺序你怎么保证”）

**Q：RabbitMQ 怎么保证顺序？**  
**A**：  
 RabbitMQ 的顺序通常是“**单队列 + 单消费者**”才能严格保证，但这会牺牲吞吐。工程里常做的是“**同一业务键的顺序**”：比如按 `orderId` 做路由，让同一 `orderId` 的消息进入同一个队列（或同一个分区/同一消费者组），保证同一订单内事件顺序；跨订单不要求全局顺序。若必须并发又要顺序，就用**状态机**容忍乱序：例如收到“确认”前必须先“创建”，否则暂存/忽略。

**追问：你项目里顺序要求在哪里？**

- 订单状态流转、同一会话的消息处理、同一房间的库存事件，都是常见顺序点。

### 5）Redis 缓存一致性（DB 改了缓存怎么办）

**Q：缓存和数据库怎么保持一致？**  
**A**：  
 我一般采用“**Cache Aside（旁路缓存）**”：

读：先读缓存，miss 再读 DB 并回写缓存；

写：先写 DB，再删缓存（或更新缓存）。删缓存通常比更新缓存更稳，因为更新会引入并发覆盖问题。并发场景下会出现短暂不一致：可通过**延迟双删**（写 DB → 删缓存 → 延迟再删一次）或给缓存加合理 TTL 来降低影响。若一致性要求更高，可以用 MQ 事件驱动做缓存失效通知。

**追问 1：为什么不是“先删缓存再写 DB”？**

- 先删再写时，可能被并发读线程回填旧值导致脏缓存。  
**追问 2：缓存击穿/穿透/雪崩怎么处理？**
- 击穿：热点 key 加互斥锁/逻辑过期；
- 穿透：布隆过滤器/空值缓存；
- 雪崩：TTL 随机化、分批预热、限流降级。

### 6）Redis 分布式锁（你项目库存防超卖必用）

**Q：Redis 分布式锁怎么实现？怎么避免误删？**  
**A**：  
 常用 `SET key value NX EX ttl` 原子加锁，`value` 放唯一标识（UUID/线程标识）。释放锁必须校验 `value`，用 Lua 脚本保证“校验+删除”原子性，避免 A 线程锁过期后 B 获取锁，A 再误删 B 的锁。锁 TTL 必须合理，业务可能超时就要续期（看门狗机制）或把临界区做得足够短。

**追问：锁过期导致并发进入怎么办？**

- TTL 设足够 + 续期；同时 DB 侧再用条件更新/乐观锁兜底，形成双保险。

### 7）MySQL 索引与慢查询（最常问）

**Q：慢查询怎么定位怎么优化？**  
**A**：  
 先通过慢查询日志/监控定位 SQL，再用 `EXPLAIN` 看执行计划：是否走索引、是否全表扫、是否出现 filesort/temporary。优化常见手段：

- 建合适的联合索引，遵循最左前缀；
- 避免在索引列上做函数/隐式转换；
- 让查询尽量覆盖索引；
- 大分页用“延迟关联/基于游标”替代 offset；
- 不必要字段不查，减少回表。

**追问：联合索引怎么设计？**

- 按过滤条件的选择性、排序/分组需求、最左匹配来排；把高选择性列放前面通常更好（但也要考虑排序/范围查询规则）。

---

### 8）事务隔离级别与 MVCC（经典八股）

**Q：MySQL 隔离级别有哪些？RR 怎么实现？**  
**A**：  
 隔离级别：RU/RC/RR/Serializable。InnoDB 默认 RR。RR 通过 **MVCC（Read View + undo log）** 实现一致性读，避免脏读/不可重复读；对需要锁的场景（当前读）会用 next-key lock 在一定程度上避免幻读。工程里，读多写少场景 MVCC 很有效；写冲突时要配合索引/锁粒度控制。

**追问：你项目哪里用到事务？**

- 下单落库、库存扣减、派单任务创建等都要本地事务；跨服务用最终一致+补偿。

### 9）幂等设计（你项目 MQ/回调/重试都要）

**Q：幂等怎么做？你怎么保证“重复请求不重复执行”？**  
**A**：  
 幂等核心是给每次业务操作一个“唯一业务键”（requestId/orderId/taskId），把“已处理”的状态落到 Redis/DB。处理前先查是否已处理：已处理直接返回成功；未处理才执行并记录。  
 对 DB 写入类操作还可用**唯一索引**兜底（例如订单号唯一），即使并发重复请求也只会成功一次，其余捕获唯一约束异常并返回幂等成功。

**追问：幂等和事务有什么关系？**

- 幂等解决“重复触发”，事务解决“原子提交”；两者常要一起用，尤其是 MQ 重投递场景。

---

### 10）分布式事务（Seata / TCC / 本地消息表）

**Q：分布式事务你怎么做？为什么不用 2PC？**  
**A**：  
 2PC 强一致但阻塞、性能差、对可用性影响大。工程里更常用：

- **本地事务 + MQ（最终一致）**：主链路快、可恢复强；
- **TCC**：强控制但开发成本高；
- **Seata AT**：接入相对容易，但对 SQL 和性能、回滚日志有要求。  
 我通常会把“下单+扣库存”做最终一致：订单先落库为 PENDING，再通过 MQ 驱动库存预占，成功再确认；失败则取消并补偿，保证业务正确且系统可用。

**追问：最终一致会不会让用户看到不一致？**

- 会有短暂中间态（PENDING），所以需要前端/状态机设计：展示“处理中”，并提供查询与回调；关键是保证最终落到正确状态。

---

### 11）线程池与异步（为什么不用线程池替代 MQ）

**Q：线程池异步能代替 MQ 吗？**  
**A**：  
 线程池只解决“异步”，不解决“可靠”。服务宕机/重启会丢任务，且无法天然支持重试、死信、持久化、削峰与消费侧扩缩容。MQ 是面向“可靠事件”的基础设施；线程池适合服务内部短任务，MQ 适合跨服务/需要最终完成的业务事件。

---

### 12）雪崩、限流、降级（稳定性大题）

**Q：系统雪崩怎么防？你项目怎么做的？**  
**A**：  
 雪崩一般因依赖变慢/错误导致线程耗尽和级联失败。防护组合拳：

- **限流**：入口限流（网关/接口）、热点参数限流；
- **熔断**：依赖异常时快速失败；
- **降级**：非核心功能（AI、统计、报表）降级为缓存/模板/转人工；
- **隔离**：线程池隔离/舱壁模式，避免一个依赖拖死全服务；
- **超时与重试策略**：超时要合理，重试要谨慎且有退避；
- **监控告警**：提前发现 RT 上升/错误率上升。

## 4）高概率项目追问清单（“尽可能全” + 每题给完整答案）

下面每一道都写到你可以直接背出来的程度。

### A. 项目总体叙述与架构（最先问）

**Q1：用 2 分钟讲清楚项目，你负责什么？**  
**A**：  
 Hostex 是面向民宿职业房东的运营管理平台，解决多房源、多渠道统一管理，覆盖房态库存、价格策略、订单入住、消息中心、退房后保洁派单、财务报表，并通过小程序微店做私域成交。整体采用 SpringCloud 微服务架构：网关统一鉴权和限流，服务注册配置（如 Nacos），服务间用 OpenFeign 调用，关键异步流程用 RabbitMQ 解耦，数据层 MySQL+Redis，搜索与知识检索用 Elasticsearch，定时/补偿用 XXL-Job。  
 我主要负责两块：  
 1）消息侧 HostGPT：多渠道消息聚合 + 翻译 + RAG 检索 + ToolCalling 拉实时订单/入住数据，生成可控回复并支持转人工；  
 2）入住/退房自动化：退房后自动创建保洁任务并通知，失败可重试与补偿，保障最终完成。

**追问：你做的最难点是什么？**

- AI 可控与多租户隔离、以及自动化链路的最终一致和可恢复。

---

**Q2：为什么用微服务？不用行不行？**  
**A**：  
 可以不用。早期单体也能做，但这个业务域多、模块差异大：订单链路、消息链路、AI 调用、任务派单峰值不同，且要故障隔离。微服务能做到：

- 按业务域拆分，职责清晰，团队协作更顺；
- 热点服务（消息/任务消费者）可独立扩容；
- AI 或第三方渠道抖动时不拖垮订单主链路。  
 同时我也明确微服务成本：链路变长、分布式一致性难、运维复杂，所以配套网关治理、熔断限流、MQ 解耦、补偿任务与日志追踪来兜住。

---

**Q3：服务怎么拆的？依据是什么？**  
**A**：  
 按业务域/变化频率/依赖耦合拆：

- 订单域：订单状态机、改期取消、支付/确认；
- 房态库存域：库存日历、房态同步、防超售；
- 消息域：多渠道聚合、会话归并、翻译、快捷回复；
- AI 域：RAG 检索、工具调用编排、输出校验；
- 入住/任务域：入住节点通知、退房派单、补偿重试；
- 财务域：对账、报表、导出。  
 拆分原则：高频变化与高风险依赖（AI/第三方）独立出来；主链路（订单）尽量轻、稳。

### B. 订单/库存一致性与防超售（高频）

**Q4：你们怎么防止库存超卖？**  
**A**：  
 我会做“双层保险”：  
 1）Redis 层抗高并发：用 Lua 原子扣减或分布式锁控制并发入口，避免大量并发直接打 DB；  
 2）DB 层兜底正确性：用条件更新（`stock > 0`）或乐观锁 version，确保最终不会扣成负数；  
 3）失败处理：扣减失败返回库存不足；并对异常情况（锁超时/消息重试）做幂等与补偿，确保最终一致。

**追问：为什么 Redis + DB 两层？**

- Redis 负责性能，DB 负责最终正确；只靠 Redis 有一致性风险，只靠 DB 抗不住峰值。

---

**Q5：下单/预占库存的流程怎么设计？**  
**A**：  
 常见做法是“订单中间态 + 最终一致”：

- 订单服务先本地事务创建订单为 PENDING；
- 发 MQ 事件驱动库存服务预占；
- 预占成功回传事件，订单变 CONFIRMED；失败则订单变 CANCELLED；
- 整个过程每一步都做幂等，保证消息重投递不会造成重复扣库存或重复状态流转。  
 这样主链路快、可用性高，且失败可恢复。

---

**Q6：你怎么保证状态机不乱（比如消息乱序/重复）？**  
**A**：

- 每个订单状态变更要校验“前置状态”，不允许跨越（例如只有 PENDING 才能到 CONFIRMED）。
- 重复消息：用幂等键去重；
- 乱序消息：如果状态不满足就丢弃/延迟处理（看业务要求），核心原则是“状态只能向前推进，且推进可重放”。

---

### C. MQ 异步链路：退房派单/通知（你负责模块会深挖）

**Q7：退房后自动派保洁任务的链路怎么讲？**  
**A**：  
 退房发生时，我不会在主链路里同步做派单和通知，而是：  
 1）退房服务本地事务落库“退房完成”与“待派单任务”；  
 2）发送 MQ 事件（例如 CheckoutCompleted）；  
 3）任务服务消费事件：创建保洁任务、写任务表；  
 4）通知服务异步发送消息给保洁员；  
 5）任何一步失败：按重试策略走延迟重试；超过次数进入失败表，XXL-Job 定时补偿或人工处理；  
 6）全流程幂等：同一个 `taskId` 重复消费不会重复派单。  
 这样保证退房主流程不被外部通知抖动影响，同时保证最终一定派单成功或可追溯。

---

**Q8：你们重试怎么设计？为什么不用立即重试？**  
**A**：  
 立即重试容易形成“错误风暴”（依赖本来就抖动你还疯狂打）。我会用延迟重试：

- 第 1 次失败：延迟 10s；
- 第 2 次失败：延迟 30s；
- 第 3 次失败：延迟 2min；
- 超过阈值写失败表，交给补偿任务/人工处理。  
 延迟可以用 TTL+死信队列或延迟队列实现。

---

**Q9：消息积压你怎么处理？**  
**A**：  
 先判断是“生产太快”还是“消费太慢”：

- 消费太慢：扩消费者并发、优化慢点（外部接口/DB）、拆队列按业务键分流；
- 生产太快：入口限流/削峰、批量合并事件；
- 监控：队列堆积长度、消费 RT、失败率，提前告警。

---

### D. HostGPT（AI）深挖：RAG + ToolCalling + 可控性（最容易加分/也最容易被拷打）

**Q10：你们为什么要 RAG？不用行不行？**  
**A**：  
 不用也能生成，但会出现两类问题：

- 模型知识过时/口径不一致，回答可能和房东最新规则冲突；
- 业务规则细碎且经常变化，纯 Prompt 很难长期维护。  
 RAG 的价值是：把房东的入住指南、退订规则、收费说明等作为知识库，回答时先检索相关片段，让生成“有依据”，并且可以把引用片段一起存档用于复盘。

---

**Q11：RAG 你怎么做分片（chunk）？怎么避免召回噪声？**  
**A**：  
 分片要在“上下文完整”和“召回精准”之间平衡：

- 按语义块切，比如按 FAQ/条款段落/小标题切；
- chunk 太大：召回噪声大，prompt 变长；chunk 太小：上下文断裂。  
 常用策略：chunk 控制在几百字以内并加少量重叠；同时保存元数据（tenantId、文档类型、版本、标题、适用渠道）。检索时先用 filter（tenantId/文档类型）缩小范围，再用关键词/向量相似度召回，最后可加 rerank（如果你没做 rerank，就说“我们目前先做 filter + topK，后续计划上 rerank”）。

---

**Q12：ToolCalling 为啥必要？你到底调了哪些工具？**  
**A**：  
 凡是涉及“实时业务数据”的回答都不能让模型猜，例如：订单是否已确认、入住时间、押金金额、是否已退房、门锁密码是否已发送。  
 所以我用 ToolCalling：模型先输出“需要调用哪个工具+参数”，服务端去调用真实业务接口拿数据，再把结果回填给模型生成最终回复。这样能把 AI 的“生成能力”和系统的“事实来源”分开，显著降低胡说概率。

---

**Q13：你怎么保证 AI 不越权、不泄露隐私？**  
**A**：  
 我把控制分三层：  
 1）**输入前校验**：tenantId 必须来自鉴权上下文，不信任前端传参；用户权限不足就不允许调用涉及敏感信息的工具；  
 2）**工具层权限**：工具接口按 RBAC/资源归属校验，只返回允许字段；  
 3）**输出后处理**：对手机号/身份证/门锁密码等做脱敏策略；同时给 AI 输出加 schema 约束，只允许输出规定字段，避免夹带敏感信息。  
 再加兜底：模型异常或触发风险 → 直接模板回复并转人工。

---

**Q14：你怎么避免串租（多租户隔离）？**  
**A**：  
 tenantId 必须贯穿全链路：

- 网关鉴权解析 tenantId → 写入上下文/请求头；
- 服务层拦截器校验 tenantId，不允许“用户传 tenantId 覆盖”；
- DB 查询强制带 tenant_id；
- Redis key 前缀带 tenantId；
- ES 检索必须加 tenantId filter；
- 日志审计记录 tenantId + userId + traceId，出现问题可追溯。

---

**Q15：AI 输出怎么做到“可控”而不是作文？**  
**A**：

- Prompt 结构化：System 里明确角色、边界、语气、禁止项；
- 输出 schema：固定 JSON 结构，例如 `{intent, language, reply, cited_chunks, need_human}`；
- 引用机制：reply 必须基于 cited_chunks 或 tool_result，否则标记 need_human；
- 规则兜底：关键业务回答用模板（例如退订政策、押金说明）优先。

---

**Q16：你怎么评估 HostGPT 的效果？**  
**A**：  
 看“质量+效率+风险”三组指标：

- 质量：采纳率（人工是否直接发送）、人工修改率、引用命中率；
- 效率：平均响应时间、每人每天处理会话数、转人工耗时；
- 风险：越权拦截次数、敏感信息触发次数、投诉率。  
 同时做抽样回放：把“输入、检索片段、工具结果、最终回复”串起来看是哪一段出了问题（召回差/工具缺/提示词不稳）。

---

### E. 网关/鉴权/安全（也很常问）

**Q17：网关做了什么？为什么要放在网关做？**  
**A**：  
 网关统一做横切能力：鉴权（JWT/Token）、tenant 解析、限流、黑白名单、路由、统一日志与 traceId 注入。这样可以让后端服务只关注业务逻辑，避免每个服务重复实现一套安全与治理逻辑。网关也适合作为“服务边界”，把异常流量挡在外面，保护内部服务。

---

**Q18：JWT 怎么防篡改？过期怎么处理？**  
**A**：  
 JWT 防篡改靠签名（HS256/RS256），服务端验证签名与过期时间。过期处理通常是短 token + refresh token 或重新登录。若有“踢下线/权限变更立即生效”的需求，可以配合服务端维护 token 黑名单或版本号校验。

---

### F. 定时任务/补偿（你说用了 XXL-Job/补偿）

**Q19：为什么要补偿任务？补偿怎么设计？**  
**A**：  
 因为分布式系统不可避免会失败：通知失败、MQ 消息处理失败、第三方接口超时等。补偿的目标是“最终完成/最终一致”。设计上我会：

- 关键操作写“任务表/事件表”，记录状态与重试次数；
- MQ 重试失败写失败表；
- XXL-Job 定时扫描失败表/超时任务，按幂等方式重试；
- 每次补偿都要可观测（日志+指标），并设置最大重试与人工介入机制，避免无限重试。

---

### G. Elasticsearch（用于消息检索/知识检索）

**Q20：ES 用在什么地方？你怎么设计索引？**  
**A**：  
 ES 适合做“检索与召回”。如果你用于 RAG：每个 chunk 一条文档，字段包括 chunk 内容、tenantId、文档类型、版本、标题、更新时间等；检索时 tenantId filter + topK 召回。  
 如果你用于消息检索：字段包括会话 id、渠道、时间、关键词、翻译文本等，支持按会话/时间范围/关键词搜索。索引设计要考虑：分词器选择、字段类型（keyword/text）、常用过滤字段做 keyword，避免高基数字段乱建索引导致膨胀。

---

### H. 性能与稳定性（场景题常出）

**Q21：QPS 上来后你会先看什么？怎么定位瓶颈？**  
**A**：  
 先分层定位：网关 RT、服务 RT、DB、Redis、MQ、第三方。

- 如果 RT 上升且 CPU 高：看热点接口、线程池、GC；
- 如果 DB 慢：看慢 SQL、锁等待、索引；
- 如果 MQ 堆积：看消费耗时与失败率；
- 如果依赖慢：立刻熔断降级保护核心链路。  
 定位手段：监控面板（RT/QPS/错误率）、日志 traceId 串联、慢查询日志、线程栈/火焰图（如果没上就说“线上以监控+日志为主，必要时抓取线程栈排查”）。

---

**Q22：你怎么避免“热点 key 把 Redis 打穿”？**  
**A**：  
 热点 key：

- 互斥锁/逻辑过期避免击穿；
- 多级缓存（本地缓存+Redis）降低压力；
- 限流保护；
- key 拆分（例如按房源/日期分桶）降低单 key 热度。

---

### I. 测试与上线（面试官会问你是否“工程化”）

**Q23：你怎么保证上线质量？有没有回滚方案？**  
**A**：

- 测试：接口测试覆盖核心链路（下单/退房/派单/消息回复），关键逻辑加单测；
- 灰度：按租户/流量比例灰度发布；
- 回滚：版本可回退，配置可开关（尤其 AI 自动回复、派单自动化都要开关）；
- 观测：上线后重点盯 RT、错误率、MQ 堆积、失败表增长速度。

---

### J. 事故复盘类（非常加分）

**Q24：举一个你遇到的线上问题，怎么定位怎么解决？**  
**A（你可套模板）**：  
 问题现象：退房后保洁任务偶发没创建/通知延迟。  
 定位：发现 MQ 消费失败率升高，原因是通知接口超时导致消费线程阻塞；重试策略是立即重试导致重复打接口形成风暴。  
 解决：把通知从消费主逻辑拆出去（或缩短超时），改为延迟重试+退避，超过次数写失败表，XXL-Job 补偿；同时加幂等键防止重复派单。  
 结果：失败率下降、堆积恢复，且最终一致性可保证。

## 你要的“再多一些”：我再补一批高频“短问深挖题”（每题含答案）

下面这些特别容易被临场追加，我直接把答案也写全：

**Q25：为什么消息中心要做“会话归并”？**  
 A：不同渠道消息格式不同且可能同一个客人在不同渠道多次咨询。会话归并能把同一订单/同一客人的消息聚到一起，让客服/AI 获得完整上下文，减少误答；也方便做统计和质检。归并依据一般是渠道会话 id、订单号、用户标识、时间窗口等，并要注意多租户隔离。

**Q26：翻译在链路里怎么放？会不会改变语义？**  
 A：一般先语言识别，再把用户输入翻译成系统统一语言（如中文/英文）再做检索与生成；输出再按用户语言生成或回译。关键是：检索最好在统一语言的“知识库语言”上进行，减少召回漂移；对敏感信息（日期/金额/房号）要结构化抽取，避免翻译损坏。

**Q27：AI 流式输出怎么做？有什么坑？**  
 A：服务端用 SSE/WebSocket 转发模型 token 流。坑：连接超时、断线续传、前端拼接、以及流式内容必须也受输出约束（最好是先流式展示自然语言 reply，但结构化字段要在结束时补齐或采用分段 JSON）。

**Q28：你怎么处理 Prompt 注入（用户让 AI 泄露规则/越权）？**  
 A：把系统指令与用户输入隔离，系统指令明确禁止泄露；工具调用必须由服务端授权，不允许模型自行决定访问敏感工具；对用户输入做过滤（例如“忽略之前指令”这类注入语句只当普通文本）；输出做敏感信息检测与脱敏。

**Q29：如果 ES 检索不到知识怎么办？**  
 A：设置阈值：召回分数低或 topK 无有效片段 → 不让 AI 硬答，直接走“模板 + 转人工”，同时记录样本用于补充知识库。

**Q30：任务补偿会不会重复执行？怎么保证不会越补越乱？**  
 A：补偿必须是幂等的：每个任务有唯一 taskId、状态机推进；补偿前检查当前状态是否需要补；补偿只做“缺失步骤”，而不是重复全链路执行。并设置最大重试次数与告警，避免无限循环。

**Q31：如何设计表结构支持多租户？**  
 A：核心业务表带 tenant_id，常用联合索引包含 tenant_id；所有查询默认带 tenant 条件；对跨租户的平台侧需求，走独立接口与独立鉴权，避免租户接口被“误用”做跨租户查询。

**Q32：你们的“日志”怎么做方便排查？**  
 A：请求入口生成 traceId，贯穿网关→服务→MQ消息；日志里固定输出 tenantId、userId、orderId、traceId。异步消息也带同一 traceId，方便把一次业务链路串起来。

**Q33：为什么要区分“核心链路”和“非核心链路”？**  
 A：核心链路（下单/库存确认）优先保证正确性与可用性；非核心链路（AI 回复、报表、通知）可以降级或延迟完成。这样系统在依赖抖动时仍能“保主保命”。

**Q34：你怎么做接口幂等（不是 MQ，是 HTTP 重复点击）？**  
 A：客户端生成 requestId 或服务端生成幂等 token；服务端用 Redis/DB 记录 requestId 是否处理过，重复请求直接返回第一次结果。对写入类接口配合唯一索引更稳。

**Q35：你会怎么解释“最终一致”给面试官？**  
 A：不是放任不一致，而是允许短暂中间态（PENDING/处理中），通过事件驱动、重试、补偿、幂等保证最终落到正确状态；关键是：每一步都可重放、可追踪、可恢复。
