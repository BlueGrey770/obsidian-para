# Seata 四大核心分布式事务模式（AT/TCC/XA/SAGA）详细对比

Seata 提供的 **AT、TCC、XA、SAGA** 四大核心模式，均围绕分布式事务一致性设计，但在**实现原理、一致性级别、业务侵入性、性能、适用场景**上存在**本质差异**，分别适配从「通用互联网高并发」到「金融强一致」、「长流程柔性事务」的全场景需求。其中**AT 是 Seata 主推的通用型方案**，TCC/XA/SAGA 为补充方案，覆盖特殊业务场景。

以下从**核心定义、实现原理、12 个核心维度全对比、典型适用场景、核心选型建议**四个层面，做最详细、可落地的区分，同时提炼各模式的核心优势与痛点，帮你精准匹配业务需求。

## 一、四大模式核心定义（设计初衷与核心定位）

先明确各模式的底层设计逻辑和核心定位，是理解差异的基础：

### AT 模式（Automatic Transaction）：自动事务

Seata **主推的通用型无侵入方案**，基于**应用层柔性两阶段提交（2PC）** 实现，通过 SQL 自动拦截、数据前后镜像、行级全局锁等机制，让分布式事务像本地事务一样易用，适配 95% 以上的互联网通用场景。

### TCC 模式（Try-Confirm-Cancel）：尝试 - 确认 - 取消

**强侵入的定制化方案**，遵循经典 TCC 分布式事务协议，要求业务层手动实现「Try（资源预留）、Confirm（最终提交）、Cancel（业务回滚）」三个方法，将事务控制权完全交还给业务层，支持任意资源类型的精细化控制。

### XA 模式：数据库原生两阶段提交

对**数据库原生 XA 协议**的轻量无侵入封装，基于**数据库层强一致性 2PC** 实现，将分布式事务的协调权交给数据库，Seata 仅负责全局事务生命周期管理，是数据强一致性的 “终极保障”。

### SAGA 模式：长事务柔性补偿

基于**事件驱动的长流程事务方案**，将一个大的分布式事务拆分为多个**独立的本地事务**，通过 “正向执行 + 反向补偿” 实现最终一致性，支持事务暂停、重试、并行执行，专为**长流程、低并发、柔性需求**的业务设计。

## 二、四大模式核心实现原理（底层执行逻辑）

各模式的核心差异源于底层实现原理，其中 AT/XA 基于 2PC 思想，TCC 是业务层 2PC，SAGA 是**无锁的一阶段提交 + 补偿**，完全脱离 2PC 框架。

### AT 模式：应用层自动化柔性 2PC（最终一致性）

1. 全局事务开启：入口方法加`@GlobalTransactional`，生成全局 XID 并透传至所有参与服务；
2. 第一阶段（本地提交）：RM 自动拦截 DML 语句，执行前生成**前镜像**、执行后生成**后镜像**，序列化存入`undo_log`表；为数据行加**Seata 行级全局锁**，**数据库执行普通本地事务并直接提交**，即时释放数据库行锁；
3. 第二阶段（异步清理 / 自动回滚）：

   - 提交：TC 收到所有分支成功后，RM 异步删除`undo_log`镜像，释放全局锁（无数据库操作，性能极高）；
   - 回滚：TC 收到任意分支失败后，RM 从`undo_log`读取前镜像，**自动生成反向补偿 SQL**执行，恢复数据至事务前状态。

### TCC 模式：业务层手动化 2PC（最终 / 强一致性可选）

1. 全局事务开启：同 AT 模式，加`@GlobalTransactional`并透传 XID；
2. Try 阶段（业务准备）：手动实现，核心做**资源预留 / 状态冻结**（如冻结库存、冻结余额），保证资源独占性，需实现幂等性、可重试；
3. Confirm 阶段（最终提交）：TC 确认所有 Try 成功后，触发手动实现的 Confirm 方法，执行**资源实际扣减 / 状态最终更新**，需实现幂等性、不可回滚；
4. Cancel 阶段（业务回滚）：TC 检测到任意 Try 失败后，触发手动实现的 Cancel 方法，执行**资源释放 / 状态回滚**（如解冻库存、解冻余额），需实现幂等性、可补偿。

### XA 模式：数据库层原生强一致性 2PC

1. 全局事务开启：同 AT 模式，加`@GlobalTransactional`并透传 XID；
2. 第一阶段（XA 准备）：每个参与服务创建**数据库 XA 分支事务**，执行业务 DML 但**数据库不实际提交**，仅标记为 “准备完成”，**持有数据库原生行锁不释放**（保证强一致），向 TC 上报准备结果；
3. 第二阶段（XA 提交 / 回滚）：

   - 提交：TC 收到所有分支准备成功后，向数据库发送 “XA 提交”，数据库执行最终提交并释放行锁；
   - 回滚：TC 收到任意分支准备失败后，向数据库发送 “XA 回滚”，数据库执行原生回滚并释放行锁。

### SAGA 模式：长事务拆分 + 正向执行 + 反向补偿（最终一致性）

1. 事务拆分：将大的分布式事务**拆分为多个有序的本地事务步骤**（如 “创建订单→扣减库存→支付扣款→物流发货”），每个步骤为独立的本地事务；
2. 正向执行：按顺序依次执行所有本地事务步骤，每个步骤执行成功后**直接提交**，无锁、非阻塞；
3. 补偿执行：若任意步骤执行失败，**按逆序执行对应步骤的补偿方法**（如 “物流发货失败”→补偿 “回滚支付扣款”→补偿 “恢复库存”→补偿 “取消订单”），每个补偿方法实现 “正向操作的反向逻辑”；
4. 核心特性：支持**事务暂停、重试、并行执行、手动干预**，适配长流程业务的柔性需求。

## 四、四大模式典型适用场景（精准匹配，避免用错）

各模式的选型核心是 \*\*“业务需求适配”**，而非 “技术优劣”，以下是各模式的**专属适用场景 \*\*，覆盖绝大多数分布式业务场景：

### AT 模式：95% 以上的互联网通用高并发场景【首选】

#### 核心适用场景

纯关系型数据库操作、对**性能 / 并发要求极高**、能接受最终一致性的**互联网通用业务**，是 Seata 的**默认首选方案**。

#### 典型案例

电商订单创建、商品秒杀 / 限购、用户支付扣款、物流状态更新、社交平台数据同步等。

#### 核心优势

无侵入、开发效率高、性能接近本地事务、高并发，完全适配互联网业务的核心需求。

### TCC 模式：包含非数据库资源的定制化业务场景

#### 核心适用场景

分布式事务中包含**非数据库资源操作**（如调用第三方接口、操作 Redis / 缓存、发送消息队列），或需要**精细化业务资源控制**（如资源预占、状态定制化冻结）的场景。

#### 典型案例

跨平台支付（调用微信 / 支付宝接口 + 本地 DB 扣减）、Redis 库存预扣 + 数据库实际扣减、调用物流接口更新状态 + 本地订单状态同步等。

#### 核心优势

定制化能力极强，支持任意资源类型，解决 AT/XA 无法覆盖的非数据库场景。

### XA 模式：核心金融 / 账务强一致性要求场景

#### 核心适用场景

对**数据强一致性有严格监管要求**（不允许中间状态、数据必须实时一致）、对性能 / 并发要求相对较低的**核心金融 / 账务业务**。

#### 典型案例

银行账务跨库转账、证券交易清算、核心支付清结算、金融机构资金划拨、保险保费扣收等。

#### 核心优势

数据库原生强一致性保障，无应用层补偿逻辑，数据一致性最可靠，故障恢复简单（由数据库负责）。

### SAGA 模式：长流程、多步骤、柔性需求的分布式事务

#### 核心适用场景

业务流程**长、步骤多、包含非即时操作**（如人工审核、物流调度、跨系统异步交互），对并发要求高、能接受柔性最终一致性的**长流程业务**。

#### 典型案例

电商全链路下单（创建订单→扣库存→支付→发货→签收→结算）、供应链采购流程（下单→供应商确认→备货→发货→入库→付款）、政务审批流程（提交材料→初审→复审→终审→结果同步）等。

#### 核心优势

支持长事务、无锁非阻塞、可手动干预、适配异步 / 人工步骤，解决其他模式无法处理的 “长流程分布式事务” 痛点。

## 五、四大模式核心选型建议（落地性强，避免踩坑）

结合实际生产经验，给出**优先级 + 场景化**选型建议，99% 的场景可直接套用：

### 优先级第一：AT 模式

**只要是纯关系型数据库的分布式事务场景，无脑选 AT 模式**—— 无侵入、高性能、高并发、开发维护成本极低，是 Seata 为互联网场景量身设计的最优解，覆盖绝大多数业务需求。

### 优先级第二：TCC/SAGA 模式（按场景选择）

- 若包含**非数据库资源操作**（如第三方接口、Redis）→ 选**TCC 模式**；
- 若为**长流程、多步骤、含异步 / 人工操作**的事务→ 选**SAGA 模式**；

### 优先级第三：XA 模式

**仅当业务是核心金融 / 账务场景，受监管要求必须强一致性时，才选择 XA 模式**—— 需接受其性能损耗和并发瓶颈，且必须确认所有参与数据库均支持 XA 协议。

### 混合模式：多模式结合使用

Seata 完全支持**混合模式**，一个分布式事务中可根据分支业务类型，灵活搭配不同模式：

- 示例：电商下单事务（创建订单→扣 Redis 库存→扣数据库余额→物流发货）

  - 创建订单 / 扣数据库余额→**AT 模式**（纯 DB 操作，无侵入）；
  - 扣 Redis 库存→**TCC 模式**（非 DB 资源，手动预留 / 释放）；
  - 物流发货→**SAGA 模式**（长流程异步操作，支持补偿）。

## 六、四大模式共同注意事项（易忽略的核心点）

尽管各模式差异巨大，但作为 Seata 分布式事务模式，有 3 个**通用要求**需遵守，否则会导致事务失效或数据不一致：

1. **全局事务入口必须加`@GlobalTransactional`**：所有模式均需在分布式事务的入口方法添加该注解，标记事务边界，Seata 据此生成全局 XID；
2. **保证 XID 全局透传**：Seata 依赖 XID 关联所有分支事务，Spring Cloud/Dubbo/Feign 等主流框架 Seata 会**自动实现 XID 透传**，若为自定义远程调用（如 HTTP 接口），需**手动在请求头中透传 XID**；
3. **幂等性是基础**：除 XA 模式（数据库原生保证）外，AT/TCC/SAGA 均需保证核心方法的**幂等性**（避免重复执行导致数据异常），尤其是回滚 / 补偿 / 重试场景。

## 核心总结

Seata 四大模式的差异，本质是 \*\*「一致性、性能、侵入性、场景适配」的不同取舍 \*\*，核心选型逻辑可概括为：

1. **纯 DB 操作 + 高并发→AT 模式**（通用首选，无侵入高性能）；
2. **含非 DB 资源 + 定制化→TCC 模式**（强侵入，支持任意资源）；
3. **金融强一致 + 纯 DB→XA 模式**（数据库原生，强一致低性能）；
4. **长流程 + 多步骤 + 柔性→SAGA 模式**（无锁，支持长事务 / 人工操作）。
